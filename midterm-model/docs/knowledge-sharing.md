# 中期选举模型知识共享约定

## 1. 现有知识面与真实可见性

本项目有三种不同用途的知识载体，不能混为一谈：

- `memory-lessons/lessons.jsonl` 是机器可匹配的操作教训库。每行必须恰有 `id`、`trigger_patterns`、`lesson`、`source` 四个字段；`lesson` 不超过 80 字；`trigger_patterns` 是 Python 正则数组；`id` 全库唯一。详细证据写在 `source` 指向的 run 日志或研究报告中，不向 JSONL 增加证据字段。
- `memory-lessons/tiers.json` 是独立的认识论分层表。它不参与当前匹配或注入，也没有被现有自检完整校验。审计时教训库已有 215 条，而分层表只有 92 项；本轮按合同不修改该表，因此新条目也暂不登记 tier。
- `memory-consolidated/*.md` 是从历史 review、surprises 与部分 run 日志生成的主题史。目前只被 hub 用修改时间计算巩固节拍；生产适配器不会把它自动注入 agent。它不能替代教训库。

各 agent 的当前路径如下：

| agent / 角色 | 当前读取路径 | 自动获得项目教训 |
|---|---|---|
| Codex 实现者 | `adapters/codex_dispatch.py` 从合同的 title/objective/deliverables/constraints 匹配，最多注入 3 条，并追加 `injection-log.jsonl` | 是 |
| opencode 实现者 | `adapters/opencode_adapter.py` 要求读取 `AGENTS.md` 与合同 | 否；没有 lesson 选择器 |
| opencode 协调者 | `adapters/coordinator.py` 注入 state、方向与 schema 摘要 | 否 |
| Terra 评审者 | `adapters/terra_reviewer.py` 注入 acceptance、回执与可选派发上下文 | 否 |
| Claude / 其他 agent | 可直接读共享文件系统与 `AGENTS.md` | 可见但不自动选择 |

跨项目、跨 harness 的长期发现面是 `C:\Users\xukkx\.claude\skills\SKILLS_INDEX.md`。只有已经重复验证、足以改变下一次执行默认值的经验，才应按 `skill-manager` 协议提升为共享技能；单次模型结果先留在本项目的 run 证据和教训库中。

当前匹配器只做正则命中数与模式长度排序，没有语义相关性门或角色过滤。用完整提案做只读探针时，`state`、`run`、`PARTIAL` 等普通英文词曾误命中无关教训。因此，在把同一选择器接入所有角色前，必须先做精度与干扰 A/B；不能把“文件对所有 agent 可读”误写成“所有 agent 已可靠消费”。

## 2. L1 / L2 / L3 分类建议

- **L1 硬规则**：必须指向具体构造约束、闸、断言或自检，并有失败夹具证明会被拦截。只写“应该”而没有强制点的仍是 L2。
- **L2 软经验**：已有真实样本外或故障证据，但尚未跨周期、议院、预测截点或数据版本复现。条目必须在 80 字内写清成立边界，详细效应量留在 source。
- **L3 机制**：改变长期流程或知识积累结构，收益需跨多轮显现；不能用一次合成基准直接宣告。

本轮新增的完整周期滚动切分教训，在 `tiers.json` 补登记前不宣称层级。若 `runs/run-068/log.md` 证明泄漏闸和滚动切分测试真实通过，可在后续治理合同中评为 L1，并把 enforcement 指向对应实现与测试；若只有方法论或合成证据，则保持 L2。

## 3. 首批 lesson 候选及写入门槛

以下内容先作为观察清单，不在结果出现前预写成教训：

1. **时间与版本泄漏**：只有当坏夹具确实被拒绝，并且完整周期滚动折保证训练周期严格早于测试周期时才写；应记录具体漏点，如 `available_at`、地图 `known_at`、修订 vintage 或目标字段混入。
2. **组件增量价值**：M0、B1 以及后续 M1–M3 只有在同一扩展窗滚动样本外折上，按预注册作用层改善至少一个主指标且守住护栏，才写“保留”；未改善也要写有边界的负结果，防止以后重复引入。
3. **合成证据边界**：合成台架只能产生“实现正确”教训，不能产生“现实选举有效”教训。真实效度必须来自历史逐届、固定预测截点的回测。
4. **相关不确定性**：只有联合模拟实测出现预期同向协方差、确定性复现，并在真实回测改善议院级概率指标后，才能写成效度教训；单席边际不变不应被误判为失败。
5. **House / Senate 差异**：任何系数、组件或阈值若只在一院成立，lesson 必须点明议院与样本期；不得从 House 自动外推 Senate。
6. **概率尺子与有效样本量**：Brier、连续对数分数、CRPS、覆盖率和校准若给出冲突结论，应记录冲突与判读口径；全国参数的分析单元是完整选举周期，不是地区行数。
7. **负结果与停止规则**：被晋级闸淘汰的组件、失败原因和可重启条件同样值得记录；不得只沉淀成功项。
8. **agent / harness 故障**：只有会改变下次执行方法的可复现故障才入库；一次性环境噪声先写 receipt `surprises`，重复或有明确强制修复后再升 lesson。

## 4. 每次写回的验证顺序

1. 先重扫全库最大编号，再仅向 JSONL 末尾追加一行。
2. 回读整库，检查每行 JSON 可解析、四字段精确、ID 唯一、lesson 长度为 1–80、trigger 数组非空且每个 Python 正则可编译。
3. 检查 `source` 路径存在并包含实际命令、输出摘要、基准条件与结论边界。当前自检不验证来源；审计发现部分历史 source 只是标签或已失效路径，这是待治理债务。
4. 用目标合同做只读匹配探针，确认新条目确实命中，且没有被泛词触发的无关条目挤出前三。
5. 若登记 L1，再检查 enforcement 文件与对应失败测试真实存在；若登记 L2，写清设定坐标；若登记 L3，引用跨轮证据。
6. 用注入 / 不注入同批 A/B 检查任务通过率、误导率和 token 成本；只有净收益可复现后，才把自动注入扩展到其他 agent。

`hub/hub.py selfcheck` 会向正式 metrics 追加记录，不适合作为窄范围只读检查。教训库结构与匹配可用无写入的标准库检查先验证，再由完整合同收尾流程执行框架自检。
